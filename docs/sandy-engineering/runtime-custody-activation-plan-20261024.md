## Identity, trust and privilege decisions

Reuse existing authenticated customer identity, API admission and universal file ownership. Do not add a second principal, receipt authority or byte store. Cloud references the Runtime signed receipt on its own transaction. Post-expiry reconciliation uses separately current status authorization and exposes no handle or renewed access.

Still required before an actionable security activation request: named existing worker login/connection, scanner workload identity, signer public-key fingerprint and release identifier, immutable generation-reader implementation, canonical relation/status route, and complete revoker inventory. No qualifying scanner or suitable connection has been verified. There is no request to generate credentials now.

Proposed privilege boundaries (not executable grants): distinct non-login scanner-ingress, custody-executor and status-reader roles, bound only to an explicitly approved existing workload identity. Scanner ingress may append validated scan receipts; trust registration/revocation is a separate administrator operation. Executor may insert claims and perform terminal transitions through reviewed routines; status reader receives only authorized status projection. No role may reset a terminal claim, alter immutable receipts, enable trust, or read arbitrary customer bytes. Keep forced RLS, tenant predicates and no PUBLIC/anon/authenticated access. Exact routine grants and policies must be generated from the final adapter/schema diff and reviewed together; this plan does not claim those routines exist. Reusing BYPASSRLS service_role or the postgres maintenance login is not this proposal.
