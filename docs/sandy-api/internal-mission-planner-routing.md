# Private mission planner and clarification review

The `sandy-mission-runner` candidate delegates all planning and question-review execution to the shared application service. Both separately named v1.0.0 operations are internal, sensitive, cost-consuming mutations: `agent.missions.plan.prepare` and `agent.missions.questions.review`. Registry API/UI/AI/verified flags remain false. An HTTP/JSON caller cannot provide their process-local capabilities, choose a privileged provider profile, supply a customer identity, choose a model or run arbitrary tools. These contracts do not add public agent API routes; that catalog remains the existing eight operations.

## Preserved source and authority

The inspected production baseline was ACTIVE version 18 (archived source version 17), entrypoint SHA-256 `f4a852845706e11bec633808c3374501b17989923b48c7662bb0e1df789a46d1`, bundle SHA-256 `2de5e68bfd2ca59ae597165736d627d2d9f41fd537f27164284708da86e8cb74`. A numeric version is historical metadata, not a source guard. Pinned instructions are recorded in `sandy-mission-runner/legacy-policy-source.json` and checked against the shared fixed request builders.

The existing dedicated `x-email-ai-renewal-key` / `EMAIL_AI_RENEWAL_KEY` credential authenticates this automation. A Controller/customer Auth bearer, service-role bearer, QA token or another worker capability does not substitute. The service credential only opens the database connection. The shared capability binds an actual stored queued **plan-stage** run, its customer and mission; its Auth user remains null and its principal kind is `trusted_internal_worker`. Request JSON does not select queue work. The queue remains ascending created time with batch size three.

Primary planning preserves the exact original instructions, gpt-4.1-mini, max_output_tokens 1600, omitted store option, 75-second timeout, input field order and fixed Responses endpoint. The optional clarification review preserves its original instructions, gpt-4.1-mini, store false, 900-token limit and 18-second timeout. Both reuse the same fixed server-only transport as the earlier runtime and worker profiles. Existing v4 broker and other timeout choices are unchanged. No broker token is introduced.

The original customer task window (first 2000 unarchived tasks) and breadth-first descendant loop (continuing while below 1000) remain. Equal-created-time rows now use UUID as a deterministic tie breaker; the legacy database query did not specify tie ordering. Recorded question/file/catalog arrays are likewise deterministically ordered. All existing client/active/completed work is included as context when it falls in that original window. Uploaded document names/types are context only; no document bytes are read or declared inspected. Real tool readiness is observed planning context, never evidence of executing a tool. Current authoritative answered questions are passed to the planner; the reviewer receives the last 25 nonempty answered records, bounded to 500 characters per question/answer.

## Durable phases and atomic records

A service-only one-use database claim precedes the primary paid request. An unresolved started/unknown logical mission blocks a new run ID as well as reuse of the original run. Resetting a queue row cannot mint a second claim. No provider/model request holds a database row lock.

A valid received model proposal, its actual provider response identifier/hash, normalized three-to-seven milestones and de-duplicated candidate questions are recorded **before** optional question-review admission. The reviewer capability is minted only from that recorded proposal and its server-returned actual answers/candidates. It lives in a process-local WeakMap, is consumed once, and has an independent durable phase claim. JSON, serialized proof copies, customer sessions and arbitrary prompts cannot create it.

The valid reviewer result can retain only indexes of actual recorded candidates. An empty valid index array keeps no new questions. Failed, incomplete, malformed, timed-out or lost review responses preserve all candidates and record the actual unavailable reason; they do not claim a successful review and do not repeat a paid request. A lost review persistence receipt leaves the primary operation unresolved instead of silently redispatching. Model response IDs/hashes establish received proposal provenance only, not independent provider execution proof.

The final database operation verifies the original stored context and atomically inserts milestones, supersedes only old unstarted unapproved Sandy-owned planned tasks, writes new questions and decisions, updates mission review state, completes the run, creates events and finishes the receipt. Client-owned, in-progress and completed tasks remain. Approval-required and third-party milestones stay waiting; every suggested tool remains `not_executed`. The mission waits for client information or client plan review; external_actions_performed stays zero and execution_verified stays false.

A genuine legacy defect is fixed: duplicate question keys within one model response are kept once. The old code de-duplicated only against previously stored questions, so two new equivalent questions violated the actual unique constraint after partial writes. Missing answer/file query results now fail admission rather than silently behaving like empty authoritative context. Foreign question/file tenant relationships are rejected explicitly because the older tables' individual mission/question foreign keys do not establish a composite customer scope.

## Context stability and limitations

Claim/finalization use a fixed row-lock order: actual run, actual customer, all same-customer task rows by UUID, mission question rows by UUID, then mission file rows by UUID, then the five fixed tool catalog base rows by integration key FOR SHARE. The customer lock plus the existing immediate task-customer foreign key blocks committed new-task phantoms during these short transactions. Locking all same-customer task rows preserves the original first-2000 selection against edits to unrelated rows; locking descendants alone would leave that bounded selection unstable. The actual mission/task locks and immediate question/file mission foreign keys block inserts; existing answer/file rows cannot change through the final scope comparison and atomic writes. The scope helper is VOLATILE so the post-lock comparison sees current facts. Locks are released before either provider call.

This deliberately trades short tenant-level contention for preserving the exact bounded legacy context. Existing independent writers can cause waits or a PostgreSQL deadlock abort; any failed final transaction leaves no partial plan and the service records an unknown result without paid redispatch. No multi-session race, throughput or contention benchmark is claimed. The tool catalog is a read-only view over `sandy_ai_integrations`. Actual Management API inspection confirmed its base relation and readiness calculation. The five fixed underlying rows are locked FOR SHARE in key order, with an exact-five distinct-key presence guard, so concurrent changes/deletions cannot evade the final context check and a missing-row insertion cannot silently fill an unlocked gap. This proposal-only service does not execute tools or claim readiness remains unchanged after commit.
