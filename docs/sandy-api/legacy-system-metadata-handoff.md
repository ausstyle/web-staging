# System metadata gateway handoff

Exports from `supabase/functions/sandy-system-metadata-api/gateway.ts`: systemMetadataOperations, systemMetadataGatewayContracts, systemMetadataContractMatches, isSystemMetadataOperation, systemMetadataOwnsGrant, systemMetadataRequiresUserSession and systemMetadataExecutionScope. All seven operations are owner-only, require a normal actual user session and own the final shared grant consumption/finish. Owner API keys, customer keys and worker leases are excluded. The central API must admit once and forward the same immutable proof; it must not consume or finish this grant again.

Scope: `{sandy_project_ref:"zmqlyygzqoidkcwdysok",permission_scope:"system:read",service:"system_metadata_v1"}`, plus lowercase customer_id for system.connections. Use the exported scope function for both approval/admission and dispatch. Its exact canonical JSON digest is checked independently by the backend. Connection approval is supplied to central admission under the existing scoped sensitive-read policy; no caller-selected approval or alternate target is accepted by the backend.

Internal POST body: `{operation,arguments,actor_id,tenant_id:null,credential_id:null,request_id,grant_id,admission_id,channel?:"api"|"mcp"}`. All four identity/proof IDs are UUIDs. Forward the original channel so current MCP exposure is rechecked. Transport uses the configured service bearer only between trusted API/backend services; this bearer never authenticates a customer at the central gateway. The backend default scope/project and RPC endpoint are fixed and cannot be selected by the caller.

Migrations 10700/10710 install one private contract table, one fixed registry-projection helper, one service-only proof-checking executor and exactly seven closed/unverified registry contract replacements. They depend on the installed central admission/audit schema and the 09000 bounded JSON input validator. The actual RPC is `sandy_system_metadata_execute(text,jsonb,text,text,uuid,uuid,uuid,uuid,text)`. Other metadata helpers/tables are private. Backend success contains strict operation/version/admission/request identity and an observed read result; provider_verified remains false and executability_not_implied remains true.

`system.catalog` includes disabled records; `system.operation_catalog` includes only API-exposed records. Both return explicit metadata fields, never raw schemas/dependencies. `system.operation_status` returns only the original owner's shared durable receipt and cannot replay execution. `cloud.vm.exec` remains absent from this installed executor catalogue. Legacy edge endpoints were not edited by this work.

Rebuild the fixed JSON contracts, bounded generated 10700 catalogue block and 10710 registry companion with `python supabase/functions/sandy-system-metadata-api/build_contracts.py`. Run Deno tests with `deno test --allow-env --allow-read supabase/functions/sandy-system-metadata-api/index_test.ts`; SYSTEM_METADATA_PG_EVIDENCE_PATH adds actual PostgreSQL output→strict JS schema validation for all seven operations. Execute the SQL fixture with 10700/10710 inside one complete rollback transaction, never auto-committed parts. Final test counts, query/source hashes and cleanup result are in legacy-system-metadata-validation-20261021.json and the frozen release manifest. Parent release engineering owns commit, installation, gateway wiring, deployed versions and production registry evidence.
