# Sandy product services constituent coverage

This inventory reconciles PDF sections 7.4, 7.7 and 7.15–7.19 with the new product service. The authoritative scope remains [api-scope-161.md](api-scope-161.md) and the [canonical PDF](Sandy_Autonomous_Control_API_Specification.pdf). A provider adapter, a database component assertion, an authenticated HTTP test and independently verified provider delivery are different evidence levels.

The new `sandy-product-service-api` catalogue contains **98 operations: 53 reads and 45 mutations**. Its two additive migrations are `20261021009000` and `20261021009010`, after the shared `20261021007100` principal metadata migration. Every new registry row has API/UI/AI exposure and verification disabled. No original wildcard requirement is declared complete by this inventory. No live email, WhatsApp message, payment, provider purchase or provider upgrade was performed for these changes.

The normal user JWT is forwarded unchanged through Sandy API. The product service validates it through Auth and independently derives its actor and tenant again inside its admission RPC; a service-role key only performs private provider receipt persistence. Ordinary customer actors have real Auth UUIDs. They are never replaced by an owner UUID or an opaque API-key principal. Owner operations use the established exact scoped approval and shared audit/receipt helpers.

Mutations use the UUID `arguments.idempotency_key` as the stable request ID. Reusing it retrieves the existing attempt; it cannot redispatch an uncertain send. Database workflows consume their one-use grant, persist state/evidence and finish their receipt in one transaction. Provider workflows claim first, then perform HTTP and persist a separate receipt; this cannot make external HTTP transactional with PostgreSQL. An interrupted response requires readback/reconciliation.

The product preferences govern new product send paths and internal support events only. They deliberately do not silently change production background-worker behaviour. Graph app permissions, ordinary portal/owner sessions, approved template fixtures and provider entitlements remain separate verification dependencies. Controller authentication, runtime egress and Custom Domain entitlement are not conflated with this implementation inventory.

The draft review digest includes subject, body, from/sender/replyTo, exact recipients, provider changeKey and the complete bounded file-attachment metadata. A stale database version, changed preflight digest, incomplete attachment page or unsupported item/reference attachment cannot be sent. This does not claim atomicity against external Outlook/legacy writers between Graph read and send.
