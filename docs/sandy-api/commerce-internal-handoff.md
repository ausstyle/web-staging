# 53 commerce operations gateway and release handoff

The new handler is sandy-commerce-ledger-api/index.ts. It exports createCommerceHandler and uses the same approved admission/receipt/audit boundary as product 98. Its53 operations are enumerated in contracts.json. Do not alter product 98 or insert commerce operations into the frozen product catalogue.

Gateway exports from gateway.ts: commerceGatewayContracts, commerceOperations, commerceContractMatches, isCommerceOperation, commerceRequiresUserSession, commerceOwnsGrant and commerceScopeSha256. All operations require an actual confirmed Auth-user JWT; all own their admission lifecycle. The universal API must forward that exact bearer, avoid owner/service/key impersonation and avoid its own second admission/consumption. Owner operations require the current actual owner; tenant operations resolve a normal active portal customer. commerce.executions.get is a dedicated authenticated receipt path which rechecks the original operation's principal.

Request: POST JSON `{operation,arguments,channel?:"api"|"mcp",request_id?:UUID,approval_id?:UUID}`. No other top-level keys are accepted. Reads generate request_id if absent. Every mutation requires arguments.idempotency_key UUID; an optional outer request_id must equal it. Owner mutations and sensitive owner reads need exact current approval_id. Tenant calls reject owner approval. The request is bounded at 100000 bytes. Successful outer response includes ok,operation,contract_version,request_id,admission_id,request_state,executed,reconciliation_required,result. Results always identify internal records and deny processor verification/payment execution.

RPC surface granted only to authenticated: sandy_commerce_admit(text,jsonb,text,uuid,text,uuid), sandy_commerce_execute(uuid,uuid,jsonb,text,text), sandy_commerce_get_receipt(uuid,text). Other commerce tables/functions are private, RLS protected, no direct role grants. The schema depends on installed 09000 product principal/JSON validation/mutation-evidence helpers and the central 07100 actual-actor admission schema. Migrations 09100/09110 add separate tables/contracts and start every registry row closed/unverified. No workers, provider requests or external credentials are introduced.

Rebuild fixed contracts and the bounded generated SQL catalogue/registry companion with `python supabase/functions/sandy-commerce-ledger-api/build_contracts.py`. Authored SQL functions outside the generated marker block remain unchanged. Deno tests: `deno test --allow-env --allow-read supabase/functions/sandy-commerce-ledger-api/index_test.ts`. To validate every actual PostgreSQL component output against its JavaScript schema, set COMMERCE_PG_EVIDENCE_PATH to the full-rollback evidence JSON. The rollback fixture must run with 09100/09110 inside one transaction, never against a connection that auto-commits fixture parts. Do not reapply09100 after it has been installed; use additive regression setup instead.

No commit, deployment, production verification or scope-completion claim is made by this handoff. The parent release task owns final deployment/registry evidence. Live processor handlers are still absent until an explicitly authorized processor and commercial policy are supplied; the typed closed interface cannot execute them. Data custody is documented separately in commerce-internal-lifecycle-custody.md; financial/control/consent/entitlement data is excluded from generic lifecycle erasure/restore.

The generated resource/item output schemas intentionally permit additional properties and do not require every operation-specific state/date/name field. The 53 SQL→JavaScript checks prove the strict outer envelope and declared monetary-field compatibility; they do not establish complete semantic output-schema validation. Separate PostgreSQL assertions exercise actual workflow states, totals, ownership, filters, reversals and failure receipts. This remains a closed, partially typed resource response boundary pending more specific per-operation result schemas.

Every aggregate response page has a database-enforced 192000-byte result budget beneath the 600000-byte RPC transport cap. When the byte budget trims items before the requested row count, possibly_truncated remains true and next_cursor identifies the last returned ID. Continuing with that cursor includes all remaining records without skipping a trimmed row. A single oversized existing record fails explicitly instead of returning a silently empty page. The real rollback fixture reads 21 invoices, including 20 legitimate large records, through all bounded pages exactly once; the default bounded JavaScript transport consumes the actual returned large page. Forwarding-status receipt lists accept limit/after_id and use the same budget.

Invoice source linkage is customer-asserted. invoice_source_correspondence_verified is always false: observing or verifying delivery of the linked source message does not establish that its amount, counterparty or content corresponds to the internal invoice, and never establishes payment.
