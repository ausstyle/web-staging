# Financial subject-text redaction

This staged family adds five executable owner-authorized policy operations for six explicit financial resources. It redacts selected customer text while preserving financial rows, balances, amounts, identifiers, history, states, versions, timestamps and permission state. It does not complete tenant erasure or restore financial data. All five registry entries remain closed and unverified; this source has not been applied or deployed.

Policies identify one resource and 1–1,000 explicit owned record IDs. Each immutable policy binds the exact source digest, source cutoff, manifest/schema, current customer-consent revision, owner admission, external policy-reference UUID, basis and finite effective/expiry times. The policy cannot outlive the customer consent. The external reference is recorded with `policy_reference_verified: false`; the API does not attest its legal validity or invent a retention period.

The selected fields are account name, journal description, journal-line description, statement-line description, invoice counterparty and item descriptions, and entitlement reason. The fixed nonempty replacement is `[redacted:subject-data-request]`. Invoice item order, quantity and precise decimal strings remain unchanged. External references, permission grants, financial identifiers and control-plane copies remain retained and may still identify the customer. `complete_tenant_coverage` is always false.

Create/get/revoke/preview/apply require the existing genuine Controller owner, exact consumed central admission and source-required immutable approval. They also use the current real-customer consent record. Apply uses the existing erasure action so legal holds, retention and `allow_erasure` are enforced before execution. Revoked, expired, future-effective, consent-invalidated, already applied or source-changed policies cannot apply. Policy inspection and previews expose digests and bounded metadata, never original field contents.

The private SQL executor locks exact target rows and their tenant-owned parents. Each protected financial UPDATE uses a same-transaction, one-use lease binding the admission, policy, tenant, record ID, complete OLD/NEW row digests and fixed transformation. Trigger authorization uses no session GUC. The original posted-journal, posted-line and issued-invoice restrictions remain effective for all paths without the exact lease. Insert/delete, amount, state, identifier and version exceptions are not granted. New trigger source and full table metadata, including enabled state, are pinned; drift refuses execution. The native plan also requires the normal origin replication mode; the actual Management database role refused attempts to change that protected parameter.

Redaction does not replay workers or provider calls. Selected invoices check the customer's actual invoice-forward receipts and canonical product execution admissions, including consumed dispatches before receipt claim. Claimed/sending/submitted/unknown/needs-review receipts and unresolved admitted/consumed/unknown/accepted attempts refuse invoice redaction. Accepted historical attempts with a stored verified result, or a matching terminal receipt created after the dispatch, can settle; a missing/null status is not accepted as proof. The invoice's cached forwarding status is an additional check. Unrelated account and other financial resources continue independently.

Three additive coordination triggers serialize canonical invoice-forward admission transitions, actual receipt writes and receipt-source customer reassignment on one customer transaction advisory key. Apply takes that key once before invoice/source row locks and refuses a busy key or invoice/source row with NOWAIT. It requires the normal READ COMMITTED snapshot. Full trigger definitions and enabled state, plus both coordination/pending function bodies, are pinned. The key grants no execution authority and is never held across a network/provider call. Same-customer writes can briefly wait for this bounded local transaction; redaction does not wait behind an already busy producer.

This is a boundary on currently recorded attempts, not full stale-material prevention. The inspected current/strict product bind and archived legacy invoice-forward producer never read the six financial target tables: they use preserved email/PDF data and control payloads. An internal invoice's asserted source ID does not establish that its contents match a particular email/PDF. Uncoordinated material captured before claim, external PDFs, email content, retained product/commerce evidence/results/dispatches and future producer lifecycle rechecks remain separate engineering work. No external erasure or complete tenant lifecycle claim is made.

## Operations and integration

The operation prefix is `supabase.tenant.financial.redaction`: `policies.create`, `policies.get`, `policies.revoke`, `preview`, and `apply`. All use handler `sandy-tenant-lifecycle-api`, permission `system:write`, scope `financial_subject_text_redaction_v1`, and RPC `sandy_tenant_financial_redaction_execute(uuid,uuid,text)`. The descriptor module exports the five-operation map, exact scope and `financialRedactionResultMatches`; the shared backend must select this RPC and result matcher without consuming a second admission.

The additive consent contract extends the explicit owner-operation choices from 68 to 73 while keeping the capacity at 128. The adapter accepts only a JWT-bound normal customer client; administrative credentials are never used as a customer session. Apply migrations 07300, 07310, 07320 and 07325 only with matching reviewed gateway/backend composition. Existing deployed 07000–07295 source and SQL remain unchanged.

## Validation

Three focused Deno tests passed. The actual Management API PostgreSQL full-rollback suite passed 345 checks: service 24, original tenant 25, scalar 26, content 36, support 16, financial capture 19, financial governed execution 20, redaction 47, consent capacity 9, and the existing commerce suite 123. The committed commerce fixture remains byte-identical; the combined harness extends only its exact safe-source whitelist for the two new coordination triggers, recording original/executed hashes and the reviewed function-definition MD5. Coverage includes six positive adapters; balanced posted entries; maximum bigint and numeric precision; invoice item preservation; forged/tampered/reused leases; native mutation restrictions; foreign ownership; source/schema/guard drift; current consent, holds and retention; policy revocation, invalidation, timing and expiry; explicit current-digest binding; and independent progress when an invoice is blocked. A separate three-check, two-session database test observed a synthetic advisory-key holder, refused apply before change in under one second, and allowed nonmutating inspection. That test establishes advisory-busy behavior, not a full provider or row-lock race. Disabled-trigger drift uses only a newly created synthetic table; no live production financial guard was disabled. A separate fixture changes only a newly created, unapplied coordination trigger to WHEN(false), confirms refusal, then restores it.

Post-rollback readback returned HTTP 201: no new functions, tables, coordination triggers, indexes or operation IDs persisted; both synthetic Auth prefixes had zero users; all three original financial guard hashes were unchanged; and the current production consent contract remained the deployed 68-choice financial revision. These are real database tests using synthetic transaction-local identities and approval fixtures. They do not establish a genuine Controller approval/session test or genuine customer JWT test. No production customer records or provider assets were modified.
