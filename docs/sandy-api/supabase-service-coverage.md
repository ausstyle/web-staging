# Supabase application service coverage

This source adds 46 provider/SQL operations in `sandy-supabase-service-api` and two actual-customer-session consent operations. Registration defaults every operation to disabled and unverified. Local tests and rolled-back database component tests are not positive Controller, customer-session, or external Auth/Storage/Realtime provider attestations.

| Original requirement | Executable constituents | Deliberate limits and remaining work |
| --- | --- | --- |
| 103 Auth users | Tenant-managed users list/get/create/profile update/disable/delete | Controller identities, the dedicated machine identity and super-admin users cannot be mutated. Creation sends no mail, confirms no email and returns no password or session. Arbitrary email/password/app-role takeover is excluded. Real provider lifecycle test is outstanding. |
| 104 Auth provider/config/hooks/sessions/MFA | Existing project Auth configuration get/set remains in the provider executor; new MFA factor list/delete and paginated safe session metadata | No guessed admin session-revocation endpoint. Current-user refresh-token revocation requires a genuine current user JWT. MFA enrolment/recovery and identity-provider entitlement checks remain distinct. |
| 105 Storage buckets | Private managed bucket list/get/create/update/empty/delete | New distinctive service namespace only, with reservation and post-create ownership binding. Pre-existing buckets are never adopted. Positive provider deletion/readback/binding-release is not verified. |
| 106 Storage objects | List/get/exists/upload/update/move/copy/delete/download | Tenant-owned private bucket only; upload/update/download are bounded to 64 KiB. Signed-URL capability transport, large-file streaming/multipart, provider versioning/retention and full content verification after copy/move remain separate work. |
| 107 Storage policies | Typed per-user command/prefix list/create/update/delete | No caller SQL/roles. Restrictive companions enforce owned resource, actual tenant membership, subject, command and prefix even if another application has a broad permissive policy. Existing unmanaged buckets retain their previous policy behavior. |
| 108 Realtime | Managed private channel-definition CRUD, bounded official-SDK subscription probe, typed permissions CRUD | Channel definitions are not a global inventory of active provider clients. Deleted definitions retain closed ownership tombstones. Subscription probe uses internal provider identity and does not verify a customer's session/RLS access or disconnect existing clients. Existing database executor owns publication CRUD/list; no duplicate execution. |
| 109 Vault | Tenant-managed metadata list/get and encrypted create/update/delete | `supabase.vault.secrets.managed.*` owns an isolated namespace. Existing credential-lifecycle `create_version`/`delete` IDs and custody remain unchanged; custody-bound material cannot be overwritten/deleted here. No decrypted values in results/audit. |
| 110 Logs | Separate provider-gap executor owns this requirement | No duplicate log executor in this service. |
| 111 Tenant lifecycle | Actual confirmed portal customer gets/sets their own explicit operation consent | Consent is a prerequisite, not tenant export/erase/restore. An explicit classified manifest and recovery adapter are separate engineering work; direct `customer_id`/`tenant_id` columns alone do not prove ownership, safe disclosure or safe restore. |
| 112 Compliance | Managed resource audit, irreversible hold creation, retention extension | Reports managed coverage, expired consent and current holds honestly. It explicitly returns `complete_tenant_manifest_verified:false` and `external_audit_anchor_verified:false`. No legal-hold release or external audit attestation is invented. |

Every administrative call requires the existing owner policy, an exact approval, the central one-use grant, a current verified registry contract, and current customer consent for the exact operation. Regulatory hold creation/retention extension can restrict resources without customer consent. Destructive operations also require explicit erasure consent and reject a current hold or unelapsed retention. API keys cannot delegate these operations.

The consent RPCs derive the tenant from the actual confirmed Auth user, an unrevoked portal account, and the matching primary customer email. The internal service credential does not create or stand in for that user session. No Controller membership or customer Auth session was created for component tests.

As of the source review, 19 Deno tests and 24 real PostgreSQL component checks passed. Database tests rolled back all fixtures. They include official pinned-SDK shape checks, tenant/prefix/subject RLS evaluation, safe Vault noncredential encryption round trips, changed-policy refusal, ownership reservation/binding, unmanaged production namespace preservation, deleted-topic tombstones, legal holds, retention, expired consent and protected Controller targets. PostgreSQL's Storage deletion guard remains enabled; positive Storage deletion must be tested through the real Storage API.

Deployment and live registry evidence are recorded by the release process. None of these component results authorizes setting `verified:true` or broad family completion.
