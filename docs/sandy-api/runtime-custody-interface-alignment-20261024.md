# API custody interface alignment

This updates PR287's source-only boundary after [Runtime's catalogue assessment](https://github.com/ausstyle/web-staging/blob/6a35933da81961c847eda29e2bc72112c972017c/docs/sandy-engineering/evaluations/runtime-custody-and-source-review-20261024.md). It does not claim that the production catalogue supplies these interfaces. The candidate remains unimported by the live gateway. No new store, scanner, credential, grant or permission is created.

## API-owned inputs and invariants

`ArtifactContext` now requires server-resolved `customerId` and explicit `tenantId` (UUID or null), alongside actor/admission, exact operation/repository/path/ref, and input/contract/scope digests. These fields enter the canonical binding digest. Request JSON, matching actor IDs, universal-files metadata, or a tenant/customer naming convention cannot establish that relation. Runtime's canonical owner must resolve and authorize it from admission and artifact records. Artifact owner customer and tenant must match independently of the digest; tests reject a forged matching digest with foreign customer/tenant.

`verifyScan` now returns a structured trusted receipt or null, replacing Boolean success. API requires exact receipt ID, artifact, immutable generation, SHA-256, size, binding digest, clean verdict, scanner identity/version and unexpired lifetime. Identity/version are bounded opaque identifiers; their trust and current validity must be established by the canonical scanner owner, not merely string validity. A receipt cannot authorize bytes from a different generation. The earlier of artifact and scan expiry bounds streaming and publication.

`SealedArtifact.authorityRevision` is captured with the durable claim. `PrivateArtifactStage.seal(proof, fence)` receives that expected revision, exact customer/tenant, scan receipt and expiry. Runtime must re-read canonical relation, claim lease, scan validity and revocation under the SAME transaction/revision lock used by revocation writers; only then consume the claim and publish the private handle/receipt atomically. `revalidate` is an early refusal check and cannot replace this transaction. The API passes the old revision even if revocation occurs after revalidation. A failed or lost seal acknowledgement remains unknown and retains private evidence without retry/discard.

## Runtime-owned implementation and acceptance

Implement these methods in the canonical runtime interface source being proposed: `withClaim`, `verifyScan`, `openGeneration`, `stage`/`seal`, `revalidate`. Add owner-side durable reconciliation by admission/artifact/binding to distinguish committed seal, definite noncommit and unresolved outcome. Do not substitute `sandy_provider_artifact_deliver`, broaden its 1 MiB owner-only contract, or create a parallel repository artifact worker. API intentionally defines no table names or new identity relation.

Required owner integration tests: concurrent duplicate claim; same actor with foreign customer; generation substitution; scanner withdrawal/expiry; revocation between revalidation and seal; process death before seal; committed seal with lost acknowledgement; reconciliation without second publication. API's twelve passing source tests establish its own byte, binding, receipt, expiry and fence behavior; they do not prove database atomicity, scanner trust, live identity mapping or provider acceptance.

Next implementation input is Runtime's concrete canonical adapter/transaction design, coordinated with Cloud's candidate scanner receipt owner. Source implementation is already authorized. Production activation needs an exact reviewed schema/adapter release and identified existing scanner/revocation writers sharing its lock; that is a bounded future release decision, not a request for a blanket grant. No Owner action can substitute for missing implementation. Binary family117 remains unaccepted until this binding and normal-path provider lifecycle evidence exist; tree118 retains its independent source tests and prior evidence.

## Compatibility review of Runtime PR303

Reviewed exact Runtime source `996e510eec7f122e960aea28dae09f7f69707913`, alongside API PR287 and Cloud's `PostgresCommitBoundary`. The shared journal direction is compatible: one receipt authority, immutable signed attestations, one INSERT-only claim, revision recheck at atomic seal, and no production trust established by fixtures. The following are concrete source integration requirements, not requests for new grants:

1. **Return canonical claim authority.** `ArtifactJournal.acquire` currently returns only leaseToken/expiresAt/record. Return `authorityRevision`, `customerId`, and explicit `tenantId` from the same `owner` resolved inside that transaction. API's `SealedArtifact`/`SealFence` requires those fields. Do not fill them from caller context or perform a second unbound lookup. Retain the lease token privately; map attestation `issuer/release` to scannerIdentity/scannerVersion and `CLEAN` to `clean` only after journal signature/trust validation.
2. **Conservative integer lease time.** `extract(epoch from expires_at)*1000` can be fractional because PostgreSQL timestamps have microsecond precision. API requires a safe integer expiry. Return `floor(extract(epoch from expires_at)*1000)` and validate its numeric range; flooring shortens authority rather than extending it. Include the lease expiry, not only the longer scan expiry, in API's record/fence.
3. **Cloud needs validation on its supplied transaction.** `scan`/`trusted`/`admitted` are private, while public methods each start `db.transaction`. Cloud must call validation inside its existing commit transaction; a nested or separate transaction loses the lock guarantee. Expose a narrow `verifyScanInTransaction(tx, binding, receiptId)` (or equivalent) that performs canonical admission/customer/file/trust checks and holds the same locks until the caller commits. Keep the repository `seal` claim separate from Cloud's upload commit; do not consume one claim for two effects.
4. **Invalid clock must fail closed.** An isolated review signed a synthetic expired receipt and confirmed `verifyScanSignature(..., 101)` rejects it but `verifyScanSignature(..., NaN)` accepts it. Require finite safe integer nonnegative current time before expiry comparisons. This is defensive validation; the existing journal obtains time from PostgreSQL, so the reproduction is not evidence of a live exploit. API's corresponding invalid-clock expiry gap is fixed in this PR, with refusal before opening bytes and after revalidation before sealing.
5. **Post-expiry recovery remains unresolved.** Current `reconcile` calls `admitted` and `scan`, so it cannot recover a committed-but-lost seal after admission completion/expiry or scan expiry/revocation. Preserve that refusal and the SEALED row. Define a separate currently authorized status-only reconciliation path before lifecycle activation; do not extend expired authority or return private handles merely to make recovery pass. The normal owner/operator scope and response projection need agreement, not a blanket grant.

Runtime still owns the connection-pinned transaction implementation, shared lock adoption by every revoker, scanner catalogue, durable claim journal and provider staging. API owns exact context digest, customer/tenant consistency, byte/generation/hash verification and fence inputs. Cloud owns reuse inside its existing commit transaction and reference to the shared receipt. A production principal/customer resolver must use proven canonical relations; this review does not invent a mapping table or assume UUID equality.

Validation: 13 API custody tests pass; synthetic Ed25519 reproduction performed locally with no production key or trust insertion. Runtime's four PGlite tests are source evidence only; real PostgreSQL multi-session lock/race tests and actual scanner/provider generation custody remain outstanding. Event246 remains partial and Runtime retains cleanup ownership; no mutation acceptance rerun is part of this review.
