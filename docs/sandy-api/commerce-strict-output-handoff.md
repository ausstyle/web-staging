# Commerce v1.1 required result contracts

This additive revision replaces the broad resource schemas on the same 53 internal commerce operation IDs with required, explicit resource projections. It changes contract hashes and response contract_version to 1.1.0. Accepted arguments, financial tables, existing business SQL, current-user/tenant resolution, grants, rate limits, audit records and execution receipts keep the existing engine. It adds no payment processor or external request.

Deploy strict_entry.ts under the existing sandy-commerce-ledger-api function slug, with 09120 and the matching strict_gateway.ts revision in Sandy API. The new entry calls createCommerceHandler with the strict catalogue; one AJV instance compiles the selected contracts. Calling createCommerceHandler with its existing single argument retains the v1.0 catalogue and behavior. API16 and the original backend1 release were pinned against commit05d0431 and do not constitute a deployment of this revision.

The gateway must replace the existing 53 commerce contract entries coherently. Exports are commerceStrictOperations, commerceStrictGatewayContracts, commerceStrictContractMatches, isCommerceStrictOperation, commerceStrictOwnsGrant, commerceStrictRequiresUserSession and commerceStrictScopeSha256. Every operation owns its actual-user admission lifecycle. The request and authentication interface stays as documented in commerce-internal-handoff.md: forward the real confirmed Auth bearer, never a service/owner/key surrogate; pass operation, arguments, optional channel/request_id/approval_id; reads may generate request_id, mutations require a stable UUID idempotency_key. Scope and registry hashes use the selected1.1 contract hash. Never perform a second owner admission around this tenant lifecycle.

The new schemas require explicit configuration and consent variants, accounts, journals and lines, manual statements and lines, reviewed reconciliation candidates, invoices and lines, plans/prices, entitlements, reports, mutation audit records and original-operation receipt results. They reject unknown resource fields, missing state/name/date/version fields, malformed UUIDs/dates, numeric monetary coercion and fabricated provider/payment verification. Posted journals require posted_at; drafts require its absence by null. Reconciliation candidate cardinality and reviewed timestamps match the recorded state. A pending or known-failed replay remains a truthful empty/failure envelope instead of being coerced into a successful resource. Receipt readback selects the original operation's result schema. Cross-field financial arithmetic and authorization remain tested business-SQL invariants; JSON Schema does not prove them.

Migration09120 locks and compares all53 existing private and registry contracts against the exact v1.0 source (or the already-installed exact v1.1 contract), rejecting drift. It replaces only contracts and registry metadata, preserves prior evidence under prior_contract_revision, and closes every exposure/verification flag. It does not relabel prior v1.0 evidence as v1.1 verification. Applied09100/09110 bytes are unchanged. Build only with build_strict_contracts.py; do not run the v1.0 generator against applied migration files. The portable supabase/tests/build_sandy_commerce_strict_migration_rollback.py emits a full rollback test using the actual migration guard: an exact repeated revision is accepted and deliberately changed private/registry contracts are rejected in rolled-back subtransactions.
