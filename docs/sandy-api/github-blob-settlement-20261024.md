# Immutable Git blob settlement — source candidate

This is a bounded family 118 implementation slice under SANDY-ENG-0005. Existing `github.git.blobs.create` can create immutable objects but currently remains `accepted`; this candidate adds effect proof and the existing durable transition to `succeeded`. It does not expose `github.git.get_blob`, authorize new operations, create a provider object or certify the family. Tree settlement and remaining family lifecycle cases are still outstanding.

The provider verifier computes the Git blob SHA-1 over the exact Git header and requested bytes, then performs a fixed-repository immutable GET and compares SHA, byte count, base64 encoding and every byte. UTF-8 (default) and base64 are supported up to 65,536 decoded bytes. Invalid encodings, malformed Unicode, oversized inputs and mismatched response identities cannot produce proof. The returned proof contains hashes and length, not file contents. Failed readback or settlement preserves `accepted` and never repeats the mutation.

The SQL candidate preserves the existing identity, input-digest, approval/job, state and audit rules. It accepts only the existing canonical blob creation operation, verifies the requested content independently with pgcrypto, and requires exactly the seven proof fields. Successful duplicate settlement reuses the proof without another audit; an audit failure rolls back both admission and job changes. A SHA-256 guard against the captured current function definition prevents replacing a newer verifier. CREATE OR REPLACE preserves the existing ACL; no grants or registry flags change.

Validation comprises 13 immutable-readback tests, the provider-handler integration suite, and 26 isolated PostgreSQL state-machine checks. The PGlite harness uses PostgreSQL's built-in SHA-256 and a fixed Node SHA-1 vector because its distribution does not include pgcrypto; this is not live pgcrypto integration evidence. It verifies actual PL/pgSQL control flow, baseline rejection, ACL preservation, proof mismatch, tenant/authority/nonce binding, duplicate settlement and transactional audit failure. Provider integration checks one POST followed by one GET and keeps an unsuccessful settlement pending.

No live blob acceptance or deployment is claimed. Production remains provider API v31. A future protected rollout needs an exact migration/function manifest, independent CI, captured current module sets and rollback bytes, genuine scoped Owner approval and the shared-component lease. The provider and gateway consume the shared mutation semantics, so both deployed bundles must be reconciled before rollout; changing repository shared files alone is insufficient. The PR246 single-entry manifest does not approve or include this slice. Apply the guarded verifier before producing blob proofs, and verify all affected deployed modules and JWT. Rollback must preserve any already-recorded genuine evidence and refuse to overwrite later releases.
