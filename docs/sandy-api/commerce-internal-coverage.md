# Provider-neutral commerce follow-up

This implementation adds 53 executable Sandy API contracts: 26 reads and 27 mutations. It addresses independently implementable constituents of requirements 158/159/161 and PDF 7.16, 7.17 and 7.19. It does not complete any additional original wildcard requirement or establish a verified payment operation. The separate frozen 98-operation product boundary remains unchanged.

| Constituent | Executable internal behavior | Remaining dependency or engineering |
|---|---|---|
| Ledger and financial audit | Tenant accounts; editable draft journals; balanced posting; immutable posted entries and lines; explicit single reversal; decimal-string trial balance, account ledger and income/expense reports; retained scoped mutation evidence | These are user-authored internal records. They are not bank balances, accounting certification or provider settlement evidence. External statement ingestion needs a selected authorized financial provider. |
| Manual reconciliation | Bounded manual statement import/read/delete; exact reference/account-amount candidate matching; persisted proposals; explicit versioned review rejects unmatched or ambiguous lines and changed snapshots | Manual statements remain unverified. No bank API is selected. Reconciliation never marks an invoice paid. |
| Invoicing | Exact integer totals, user-declared unverified tax, versioned draft edits, serialized internal invoice numbering, issue/void and readback | Issue does not deliver an invoice or initiate payment. Void is not a processor refund. Legal invoice/tax policy and processor workflows remain unconfigured. |
| Existing invoice forwarding | Reconcile an owned source-message forwarding receipt; distinguish claimed/sending/submitted/verified/failed/unknown; retain payment_status=unverified | Existing Wise-address forwarding is not payment processing. The component fixture uses a synthetic submitted receipt inside ROLLBACK, not a provider delivery. Live send remains closed. |
| Commercial consent | Bounded expiring customer-authored terms-version/forwarding/renewal records and explicit revocation; current record readback | The record explicitly has terms_validated=false and authorizes_processor_charge=false. Approved legal terms, recurring-payment mandates and a chosen processor are still required. This is separate from scope 111 erasure/export consent. |
| Product plans/prices | Owner-approved actual internal plan creation, versioned update/archive, immutable price values and archive | No provider price, purchase, subscription, entitlement enforcement in existing frontend or recurring billing is created. Customer checkout/subscription workflows require an explicit processor and commercial policy. |
| Entitlements | Exact owner-approved bounded grants/revocations to an existing customer; actual customer list/check with expiry and revocation | These are explicit internal feature records, not paid access or provider entitlements. Integrating existing product feature enforcement requires an approved feature catalogue and entitlement policy. |
| Payment intents, refunds, payouts, taxes | Explicit truthful capability/configuration result and typed closed processor interface | No processor has been selected. These live handlers remain engineering dependent on processor selection, merchant/test account binding, approved commercial/currency/tax policy, scoped secret reference and an authorized provider test fixture. The interface is not counted as an executable payment handler. No charges, refunds, payouts, purchases or provider upgrade occurred. |

All 53 registry rows are installed closed: api_exposed/ui_exposed/ai_exposed=false and verified=false. Component evidence does not authorize exposing them or issuing a real customer session. All public results state source=internal_commerce_records, payment_executed=false and provider_verified=false. Monetary inputs and outputs are decimal strings; actual PostgreSQL→JavaScript fixtures include 9007199254740993 and totals above JavaScript's exact integer range.

Actual-JWT tenant identity is independently resolved from the confirmed Auth user, current portal account and verified primary customer address. Owner catalogue/configuration operations use the existing owner check and exact immutable approval; sensitive owner reads also require approval. Customer keys and service-role credentials cannot substitute for a normal session. Every operation is nondelegable to API keys and uses current exact registry/schema/hash/exposure checks. The normal tenant path shares central admission, rate-window, one-use grant, audit and receipt infrastructure while retaining the real actor and tenant.

Internal workflow effects, grant consumption, before/after evidence, hash-linked audit, result and receipt finish share one PostgreSQL transaction. Known validation/state failures roll that workflow back and persist a terminal unexecuted failed receipt with no invented provider HTTP status. Transport failures retain an unknown outcome and prohibit automatic redispatch. Successful internal mutations use the central conservative accepted state; its200 value describes the internal RPC result, not a processor response, paid invoice or bank settlement. Posted ledger data uses reversals instead of destructive correction. Normal PostgreSQL sequence allocation gaps after ROLLBACK are accepted by the existing hash-link audit verifier; sequences are never reset or locked to conceal gaps.

The PostgreSQL component fixture creates synthetic Auth users, portal bindings and owner approval rows only inside one complete transaction ending ROLLBACK. It is not an HTTP Auth session. It checks the real 60/min tenant limiter, then removes only the newly created synthetic actor's transactional rate-window fixture between independent phases. No production user's rate limit, role, sequence, secret or policy is changed. All trigger sources used by fixture writes are pinned; customer Drive provisioning is excluded and memory capture disabled. No external request or lasting user/key is created.

Final exact test counts, query hashes, cleanup result and frozen source hashes are recorded in commerce-internal-validation-20261021.json and the release manifest. Provider reads and deployed HTTP user-session tests remain separately unverified until the actual normal-session/provider fixtures exist. Root release engineering owns commits, permanent migrations, deployment versions and central registry evidence updates.

The generated resource/item output schemas intentionally permit additional properties and do not require every operation-specific state/date/name field. The 53 SQL→JavaScript checks prove the strict outer envelope and declared monetary-field compatibility; they do not establish complete semantic output-schema validation. Separate PostgreSQL assertions exercise actual workflow states, totals, ownership, filters, reversals and failure receipts. This remains a closed, partially typed resource response boundary pending more specific per-operation result schemas.

Every aggregate response page has a database-enforced 192000-byte result budget beneath the 600000-byte RPC transport cap. When the byte budget trims items before the requested row count, possibly_truncated remains true and next_cursor identifies the last returned ID. Continuing with that cursor includes all remaining records without skipping a trimmed row. A single oversized existing record fails explicitly instead of returning a silently empty page. The real rollback fixture reads 21 invoices, including 20 legitimate large records, through all bounded pages exactly once; the default bounded JavaScript transport consumes the actual returned large page. Forwarding-status receipt lists accept limit/after_id and use the same budget.

Invoice source linkage is customer-asserted. invoice_source_correspondence_verified is always false: observing or verifying delivery of the linked source message does not establish that its amount, counterparty or content corresponds to the internal invoice, and never establishes payment.
