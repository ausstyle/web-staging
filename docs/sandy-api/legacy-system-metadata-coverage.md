# Seven legacy system reads

The new `sandy-system-metadata-api` implements seven existing registry IDs through one bounded, typed, owner-authorized backend. It adds no provider mutation and does not complete an additional original wildcard requirement. All seven retargeted registry rows start closed and unverified. Existing deployed legacy functions retain their original source bytes; root release engineering owns the canonical gateway composition and deployment.

| Existing operation | Actual source finding | New executable behavior |
|---|---|---|
| system.catalog | sandy-system-introspection v6 reads the entire registry with raw schemas | Bounded, searchable/filterable registry metadata including disabled registrations; explicit names, permissions, handler and recorded flags only. Authorized schemas remain available through central Sandy API describe. |
| system.operation_catalog | sandy-operation-catalog v2 uses GET and returns only api_exposed registrations, including raw schemas/dependencies | The canonical API POST route preserves its exposed-only distinction and uses the same safe registry projection/pagination as system.catalog. No schema or dependency blob is returned by this metadata service. |
| system.capabilities | Introspection v6 reads up to 500 capability-runtime records | Typed keyset pages with feature/channel/health/time filters; scope_key is replaced with a stable fingerprint; recorded auth/implementation/health/deployment states retain checked_at and explicitly do not verify a live provider. |
| system.runtime | Introspection v6 reads the 100 latest recorded runtime states | Checked-time/keyset pages with deterministic tie-breakers and NULL-time continuation. Recorded deployment_version does not attest the currently executing function or current provider connectivity. |
| system.connections | Introspection v6 derives a customer and reads local Composio connection records | An actual current owner must name an exact existing customer target and obtain scoped sensitive-read approval. Only provider slug, recorded status, company UUID, update time and an opaque pagination fingerprint are projected. Raw provider account IDs, tokens, scopes, ciphertext and live-readiness claims are excluded. |
| system.coverage | Introspection v6 counts registry flags and lists unverified IDs | Counts apply to explicit filters; the unverified-operation list is paginated. The response expressly states that original 161 completion is not established by registry row/flag counts. |
| system.operation_status | Registry points to sandy-operations-api; archived introspection returns 501 for receipt lookup | Actual same-policy alias to the current owner's shared durable execution receipt. It checks exact target request UUID and never redispatches the original operation. Foreign-owner receipts remain hidden. |
| cloud.vm.exec | Registry handler is unassigned, disabled/unverified, state executor_missing | Still a genuine missing executor. No SSH/WinRM placeholder or unrelated operation is substituted for its project/zone/instance/command-ref contract. |

The archived deployed sources were inspected read-only through authorized Management API access: introspection v6 SHA256 `5a4797e859e13d6be66037bb0ea9a3f99639440d1c414760a61603ab937c83e4`; operation-catalog v2 SHA256 `4611d03748d8a1d7c20a3c9fe4e7e5ab85b39a5004eb101454c038f58230fa3a`. Their source inventory is recorded in legacy-system-metadata-source-inventory.json. Registration did not previously provide a canonical executable handler for these seven rows; receipt lookup also lacked an implementation in the inspected introspection branch.

The trusted internal service transport carries a one-use admission issued only after central Sandy API authenticates the normal owner session. It does not create or substitute a service-role customer session. The RPC independently rechecks actual confirmed non-anonymous owner identity, immutable actor/tenant/key kind, exact operation/input/scope/contract/registry revision, current API/MCP exposure and nondelegable flags. Connection reads additionally use the existing exact approved-read policy bound to the customer target. Grant consumption, bounded SELECT and shared audit/receipt finish are atomic in one PostgreSQL transaction. No provider request, model call, message, key issuance or worker job is performed.

The only new table is the private, RLS-protected global `sandy_system_metadata_contracts` catalogue. It has no customer ownership, credentials, background workers or automatic lifecycle deletion/restore. Ordinary customer/key/service table grants are absent; the service role can execute only the typed proof-checking RPC, not the private registry helper. Existing runtime/connection tables retain their independent custody classification. Shared admissions/audit/receipts retain their existing control-data rules.

The PostgreSQL evidence uses fresh synthetic Auth users, local connection/customer rows and exact approval rows exclusively inside one complete BEGIN/ROLLBACK; it is not an HTTP Auth session. Inspected fixture triggers are pinned, Drive provisioning excluded and memory capture disabled. Actual production registry/runtime metadata is read with safe projections. The audit verifier follows hash links and permits ordinary sequence gaps after rollback; no sequence reset/lock is used. Real Controller-session HTTP verification and runtime egress remain separate dependencies. Neither component tests nor source installation establish that all 161 original requirements are complete.
