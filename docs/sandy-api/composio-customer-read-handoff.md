# Composio customer discovery and reviewed read execution

This isolated candidate implements the original `composio.discover_toolkits` and `composio.execute_read` IDs using one actual customer-session admission and one service-only dispatch. Both registry rows remain closed and unverified. No live Composio tool or real Controller session has been verified, and no original161 requirement is certified complete by this component evidence.

`contracts.ts` exports `composioReadOperations` and `composioReadContractMatches`. Central Sandy API must forward the original actual JWT, channel and request_id to `sandy-composio-read-api`, using the same owns-user-admission pattern as tenant product services. It must not create an owner grant, replace the JWT with the service role or pass actor/tenant/account overrides. The request body is exactly operation, arguments, request_id and optional api/mcp channel; approval_id and connected_account_id are rejected.

The backend authenticates a confirmed nonanonymous normal user; the authenticated admit RPC independently requires that user's current unrevoked portal account and exact normalized primary Auth email match. There is no owner substitution. The contract, live channel exposure/verification, nondelegability, input digest, tenant scope and registry revision are rechecked. Immutable private policy owns the two exact contracts. Shared admission/rate/audit storage is reused; the service-only bind independently rechecks the actual current principal and grant before consuming once and creating a one-use claim. Customer input selects an owned company or personal workspace, never an arbitrary provider account. Limits are60 requests and10 declared provider units per actor/customer minute,30KB canonical arguments,60second admission lifetime,100 local/provider inventory rows and100KB returned tool data.

Discovery compares the customer's locally recorded connections with a fresh complete provider account inventory for sandy_customer_<customer_uuid>. It returns toolkit/company/status and reviewed profile IDs, without provider account IDs or credentials. An incomplete provider inventory is an error. Execution requires exactly one active owned connection, a private enabled developer-reviewed read profile, the same fresh provider tenant/account/toolkit identity, a complete fresh provider tool inventory and exact canonical SHA256 of the reviewed provider definition. The request can supply neither endpoint nor tool slug. The only write-shaped provider request is the fixed Composio tool execution endpoint for the reviewed read profile; a prefix or description cannot prove read-only effects.

No production read profile is installed by10820/10830. Profiles require an explicit reviewed_read_only effect contract, review reference, exact provider-definition hash and strict bounded input/output schemas. Profiles are private policy, writable only through reviewed database source changes; no customer/service-role profile enrollment endpoint exists. The runtime permits a small literal schema subset with strict objects, bounded strings/arrays/depth/node count, finite safe numeric bounds and recognized credential-key exclusions. External references, arbitrary regex, open object passthrough, URL resolvers and read-name heuristics are refused. Schema-valid data is projected without surrounding provider metadata. Provider success requires successful=true and no provider error. An unreviewed or missing profile is a precise activation dependency, not an executable arbitrary-tool allowance.

The private dispatch table stores admission/claim/customer/profile IDs, status, provider HTTP status, result digest and timestamps. It stores no provider payload, arguments, provider account IDs or tokens. Contracts/profiles are global private policy; dispatches are tenant security receipt metadata, not generic customer payload or restore material. The tenant custody owner has been notified for separate inventory classification.

Request replay returns the owned receipt and digest with data=null and payload_stored=false; it never performs a second provider call or bind. Input/operation/tenant/channel conflicts are denied. Lost or schema-invalid tool responses and lost receipt persistence require reconciliation and return executed=null. Completion is attempted once. Account/tool preflight failures have no tool effect and finish failed. Auth outages remain503 rather than being relabeled invalid credentials.

The code shares the existing registry schema validator, canonical digest/bounded stream helpers, admission/rate/audit storage and global receipt completion. SQL adds a narrow bounded schema adapter because the older product SQL validator cannot represent nullable company IDs or the outer generic arguments container; ordinary primitive checks still reuse the existing validator. The profile-specific strict schema is checked again before provider dispatch and on output. This keeps one business executor for both API and MCP.

Runtime requires the private COMPOSIO_API_KEY binding and enabled composio_connector; the key is never returned. Local absence of Controller and Composio credentials does not block source/SQL tests. No plan purchase or provider entitlement change is requested.
