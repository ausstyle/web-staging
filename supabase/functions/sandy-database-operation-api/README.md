# Sandy database operation service

The initial release contains 78 contracts installed with API/UI/AI exposure and verification false. The additive maintenance release replaces three closed contracts with v2 implementations and adds one recovery read, for 79 current contracts. New source and SQL components require a separate reviewed deployment and real authorization/provider evidence before activation. Existing provider `migrations.apply`, `repair`, `rollback`, `list` and existing metadata reads are preserved.

The service implements a fixed `zmqlyygzqoidkcwdysok` Management transport, parameterized SQL reads/data writes, explicit schema/data operations, schema manifests, and a separate transactional Sandy migration ledger. Each request requires service transport authentication plus an independently verified enabled owner, exact approved one-use grant, registry contract/revision, actor, request, input and fixed-scope binding. The private SQL boundary repeats the checks. A service key never supplies a customer or owner Auth session.

Reads use actual Management `read_only:true`, assert `transaction_read_only=on`, and apply fixed per-request server timeouts. The pinned PostgreSQL parser/scanner and WASM are embedded in memory; no runtime parser filesystem/network permission is needed. Raw SELECTs are intentionally restricted to passive ordinary stored tables, reviewed catalogue metadata, builtin types/functions/operators, and simple nonrecursive/nonshadowing CTEs. Physical relation names require an explicit schema, and execution resolves operators only in pg_catalog while preserving PostgreSQL precedence. Exact read sources are locked in the Management wrapper; volatile writes acquire locks per statement after any earlier CREATE, before checking types and columns; credential-bearing source columns and nested sensitive output fail closed. Protected Sandy control/identity tables cannot be changed through generic SQL. This is an explicitly supported SQL subset, not an arbitrary administrative SQL escape hatch.

Writes use bound JSONB parameters and one transaction for the effects, existing triggers, postconditions, migration state and durable receipt. `max_affected_rows` caps the aggregate transaction. DDL changes have version/checksum/advisory-lock/before-snapshot checks and catalogue postconditions. Migration repair appends a prior-checksum revision after actual schema and smoke-test checks. Snapshots include public structures and routines, owners/ACLs, policies, reviewed role properties/memberships/default privileges, publications and sequence definitions. They contain digests, not function bodies or credentials. `supabase.sql.receipt.get` uses a fresh owner read grant to reconcile an original expired/unknown request without executing it again.

ANALYZE, REINDEX and backend cancellation/termination have explicit nontransactional semantics: acceptance and actual metadata readback do not certify a complete lifecycle, and lost responses require reconciliation. VACUUM v2 uses a reserved direct PostgreSQL session with certificate verification, fixed project hostname/database/admin role, and actual server deadlines. It issues VACUUM outside a transaction, restricts the public target and records a private command proof, actual pg_stat readback when available, and a native receipt with HTTP status null. It stays closed before grant consumption when `SANDY_DATABASE_MAINTENANCE_URL` is absent; Management's transaction wrapper and SQL relays are never substitutes. Lost responses are not retried.

Cron create/update v2 stores an immutable approved plan and schedules a fixed private wrapper through existing `cron.schedule`/`cron.alter_job`. Each run checks current owner, registry revision, approval, source safety and shared principal quotas. Standing approval is limited to 24 hours, 100 runs, an interval of at least 60 seconds, 100 affected rows and 10 active schedules per owner. Commands and postconditions run atomically; any failure pauses the schedule. Only isolated ordinary public tables without hidden trigger/rule/RLS/FK/default/custom expression effects are supported. Updates require a fresh exact approval and revision. No extension is installed automatically. A fresh approved `supabase.database.maintenance.receipt.get` reconciles native or scheduler receipts without redispatch.

Materialized view refresh requires the exact `definition_sql` deparsed under a pg_catalog-only search path. The handler parses its passive source references, locks ordinary source tables and acquires the target lock with a transactional WITH NO DATA refresh that executes no definition, and the private transaction compares that exact definition before refreshing; source/type/credential checks apply before copying rows; a mismatch rolls the original storage back. Generic passive SQL currently refuses materialized views because PostgreSQL disallows LOCK TABLE on them. All typed contracts remain disabled pending deployment and real approval evidence.

These families remain partial. Physical backup integrity/restore drills belong to the provider transport; logical replication slots/subscriptions, network webhook creation and full PL/pgSQL/custom SQL semantics require additional reviewed handlers. Trigger creation requires an explicit reviewed function SHA binding through `SANDY_DATABASE_REVIEWED_TRIGGER_FUNCTIONS_JSON`; no function approval is inferred. Existing portal/customer writes continue to use their separate actual-session service.

## Gateway integration

Import `databaseOperations`, `databaseExecutionScope` and `databaseCapability` from the lightweight `gateway.ts`. This module does not load the parser/WASM or provider SDK. Add the fixed function mapping to the gateway, compare handler/mutation/scope/contract SHA exactly, apply `databaseCapability`, require a normal owner session and verification for **all** these operations (including sensitive reads), and send the canonical actor/request/grant/admission context. Use `providerOwnsGrant:true`; this service consumes and finishes the admission at the provider boundary. Forward output through the registry schema validator. MCP discovers these operations through Sandy API only. Do not enable an operation from source tests alone.

The SQL functions are executable only by the Management database role; PUBLIC, anon, authenticated and service_role cannot call them or read the private receipt/ledger tables. Deployment must keep normal Edge JWT verification enabled.

Management handlers obtain the current private credential consumer only after consuming the execution grant. A configured active-key refusal cannot fall back to an environment credential. Apply credential-consumer migration `20261021006100` before deploying this cutover. The direct native connector has its separate explicit configuration.

## Validation

`deno test supabase/functions/sandy-database-operation-api/index_test.ts supabase/functions/sandy-database-operation-api/maintenance_test.ts` needs no permissions. It covers the original 78 plan mappings and additive maintenance dispatch, fixed native configuration/session/deadlines, approved single-effect cron compilation, standing limits, grant and consumer ordering, private native receipt binding, actual HTTP status semantics, no fallback/retry, and sensitive/unknown results.

`postgres_component_check.mjs` runs actual PostgreSQL in local PGlite, using synthetic authorization rows and no cloud connection or Auth session. Install `@electric-sql/pglite@0.3.14` into `/tmp/sandy-pglite`, then run `node supabase/functions/sandy-database-operation-api/postgres_component_check.mjs`. `SANDY_TEST_PGLITE_MODULE` and `SANDY_TEST_DENO` can select installed test tools. These checks exercise actual SQL/PLpgSQL, binding, triggers, rollback, cumulative limits, receipts/replay/recovery, all six data operations, schema/ACL drift and migration apply/repair. They do not certify deployed HTTP authentication or production verification.

`maintenance_postgres_check.mjs` exercises the real private migration and shared policy in ephemeral PostgreSQL/WASM, including native VACUUM outside a transaction and cron effects/postcondition rollback. Its scheduler interface is synthetic; it does not establish real pg_cron execution or remote direct TLS connectivity.

`generate_registry.ts` is historical and must not rewrite the applied `20261021005000`. `generate_maintenance_registry.ts` prints additive v2 metadata for `20261021005100`; installation refuses a conflicting or already verified contract cutover. Never regenerate or edit an applied migration.
