# Codex engineering instructions — Sandy AI

These rules apply to Sandy AI files, services and engineering tasks in this repository, not unrelated projects.

1. Before substantial Sandy work, read [engineering README](docs/sandy-engineering/README.md), the [Master Scope v1.1](docs/sandy-engineering/master-scope-v1.md), the [implementation program](docs/sandy-engineering/implementation-program.md) and the relevant numbered task scope. The Master Scope governs mission, privacy, non-disruption, architecture and acceptance. Its filename is stable; section 22 is the v1.1 amendment.
2. Follow the [shared architecture/ownership/contracts](docs/sandy-engineering/architecture-contracts.md). Build a modular core, not duplicate runtimes, queues, memory stores or provider executors. One logical orchestrator can have multiple leased workers.
3. For API work, also read the [161-family API scope](docs/sandy-api/api-scope-161.md). Map families to actual canonical handlers and evidence; do not use registry count as completion.
4. Every substantial objective has one scope under `docs/sandy-engineering/tasks/`, using the task template. The ten initial scopes and dependencies are in the implementation program. Add/version metadata in `docs/sandy-engineering/scopes.json`; do not create undocumented competing scope documents.
5. GitHub main synchronizes scope metadata to Supabase `public.sandy_engineering_scope_catalogue`. Do not edit synchronized fields in Supabase as the source of truth. Check `.github/workflows/sandy-scope-sync.yml` and the latest actual sync record after merging scope changes. Document sync is not software deployment.
6. The live operation catalogue/evidence is `public.sandy_operation_registry` in project `zmqlyygzqoidkcwdysok`. Registered, implemented, deployed, reachable, authorized and functionally verified are different states. Preserve that distinction and invalidate stale evidence after relevant changes.
7. Sandy's runtime uses Sandy API; external MCP clients use Sandy MCP which calls Sandy API. All callers share identity, policy, contract, idempotency, receipt and audit enforcement. Do not add a privileged parallel provider path or weaken authorization to pass a test.
8. Prioritize **SANDY-ENG-0001 runtime reasoning/reliability**. 0003 owns orchestrator implementation; 0004 mission/truth durability; 0005 API/release foundations; 0006 context/memory. Deliver the minimal foundation slices needed for real chat fixes without waiting for every API family. 0002 coordinates autonomy without duplicating these engines.
9. Inspect actual deployed source, schema, consumers and failing behavior before changing them. Preserve customer data and working functionality. Parallel tasks need isolated branches, contract compatibility and one release owner/lock per shared component. No silent overwrite or force-push recovery.
10. Use source-linked, real acceptance evidence with the [evidence template](docs/sandy-engineering/templates/acceptance-evidence.md). Unit/mocked tests are necessary but do not prove provider effects. Do not send unsolicited messages, delete customer data, buy resources or move money merely to test.
11. Record exact external credential/permission/entitlement blockers while continuing independent work. Use supported renewable delegated identities; do not store personal owner tokens in code, logs or docs, and do not bypass normal customer/Controller authorization.
12. For document-only changes, validate source/version/links/ownership and actual catalogue synchronization; do not alter production operation verification flags. For code changes, require traceable commit/artifact, staging/canary, live outcome checks and compatible rollback/forward repair. A committed scope is not implemented software.

Current order: P0 runtime/quality and its foundation slices; P1 mission/autonomy, memory and API completion; P2 calendar, video and customer experience; P3 commercial launch. Tenant isolation, truthful outcomes, credential protection and recovery controls apply from the start.
